## Storage Systems

The architecture uses a combination of specialized storage systems aligned to each of the four goals. For predicting patient readmission risk, a **Data Lake** is used to store historical treatment data, including structured (EHR records) and semi-structured data. This enables scalable storage and supports feature engineering for machine learning models. For enabling doctors to query patient history in plain English, a **Vector Database** is used. Patient records are transformed into embeddings, allowing semantic search over clinical notes and past events. For generating monthly management reports, a **Data Warehouse** is used to store cleaned, structured, and aggregated data optimized for OLAP queries such as bed occupancy and cost analysis. Finally, for streaming ICU vitals, a **time-series optimized storage (within the Data Lake or a streaming store like Kafka + object storage)** is used to ingest and persist high-frequency data efficiently. This combination ensures each workload is handled by a storage system optimized for its access pattern.

## OLTP vs OLAP Boundary

The OLTP system primarily consists of operational databases such as EHR systems and billing systems, where real-time transactions like patient admissions, treatments, and payments are recorded. These systems are optimized for low-latency writes and consistency. The boundary between OLTP and OLAP occurs at the data ingestion layer, where data is extracted via ETL or streaming pipelines and moved into analytical systems like the Data Lake and Data Warehouse. Once data enters the Data Lake, it becomes part of the analytical ecosystem, where it is transformed, aggregated, and used for machine learning and reporting. The Data Warehouse sits firmly in the OLAP domain, serving business intelligence queries, while the Vector Database bridges operational and analytical use cases by enabling fast semantic retrieval over processed data.

## Trade-offs

A significant trade-off in this design is the increased architectural complexity due to the use of multiple specialized storage systems (Data Lake, Data Warehouse, Vector Database, and streaming infrastructure). While this improves performance and scalability for different workloads, it introduces challenges in data consistency, maintenance, and operational overhead. For example, data duplication across systems can lead to synchronization issues and increased storage costs. To mitigate this, a well-defined data pipeline with clear data contracts and orchestration (e.g., using workflow tools like Airflow) should be implemented. Additionally, adopting a **Lakehouse approach** can reduce redundancy by combining Data Lake and Data Warehouse capabilities, while centralized metadata management and monitoring can ensure consistency and observability across the system.
